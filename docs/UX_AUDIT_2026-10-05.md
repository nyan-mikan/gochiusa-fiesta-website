# 点兔贺年祭网站 UX 审计报告

> 更新：本报告列出的条目已在本轮修复，详见[修复与验收记录](AUDIT_FIXES_2026-10-05.md)。以下保留首次审查时的现象、证据和建议。

日期：2026 年 10 月 5 日  
对象：投稿者、审核管理员、节目编排人员、主持稿编辑人员  
方式：真实页面交互、桌面与手机尺寸检查、键盘操作、样式测量和前端代码审查。

## 结论

目前网站的视觉风格已经基本统一，但操作体验仍有明显短板：**信息和按钮同时出现得太多，出错后缺少直接修正路径，部分操作缺少恢复机制，手机端没有完整适配管理工作。**

这不是只调整颜色或间距就能解决的问题。建议优先处理键盘弹窗、误删恢复和手机审核列表，再简化投稿与主持稿的操作结构。

本次整理 **11 项 UX 问题或改进项：3 项优先处理、7 项随后优化、1 项细节优化**。优先级按对任务完成、误操作恢复和使用频率的影响判断，不等同于上一份功能报告的故障严重等级，也不代表每一项都违反无障碍标准。

本次只做分析，没有修改产品界面或部署线上版本。上一份功能审计中的保存覆盖、取消退出失效等问题仍需优先修复，不能被视觉优化替代。

## 检查范围与证据

- 使用现有本地构建、真实本地 Worker 和隔离的 UX 测试账号；没有操作线上用户投稿。
- 桌面检查尺寸为 **1440 × 900**，手机布局检查尺寸为 **390 × 844 CSS 像素**。
- 实际操作了验证码登录、审核列表、主持稿、段落设置、投稿填写和成员移除；其余页面结合源码检查。
- 截图和页面测量均使用隔离测试活动。截图中的测试活动、测试分区数量不代表生产环境，不据此判断线上信息架构。
- 手机检查是桌面浏览器的窄视口模拟，不等同于 iOS/Android 真机、软键盘或屏幕阅读器测试。
- 判断参考 `ui-ux-pro-max` 的表单/可访问性检查方法，以及文末列出的 W3C 原始资料；布局密度、工作流和导航建议属于基于现状的设计判断，未进行真实用户访谈或任务计时。

## UX01：手机端审核列表没有真正适配

**观察：** 390 像素宽的视口中，页面内容宽度达到约 466 像素；“查看”链接位于横坐标约 375–454 像素，主要操作挤出右侧。表头“负责人”等文字被压成多行，作品名称也被迫大量换行。

列表上方的品牌、导航、活动选择及三个筛选项占据了首屏大部分空间，第一条记录在截图中只能看到一部分。横向导航和横向表格又带来了两种不同的滚动区域。

**影响：** 手机审核需要先下滑、再横向找操作；用户难以同时看清节目名、状态和按钮。

**原因：** [Submissions.vue](../src/web/pages/Submissions.vue) 使用 `table-scroll` 包装表格，但共享样式只给 `table-wrap` 配置了横向滚动；即使补齐容器滚动，也只能缓解溢出，不能解决六列表格在手机上的阅读成本。

**建议：** 手机改为记录卡片：节目名和状态在首行，负责人、时长、更新时间作为次级信息，“查看投稿”固定在卡片内。把不常改的筛选项收进“筛选”面板，同时保留已生效条件。桌面继续使用表格。

**验收：** 320、390、768 像素宽度下页面不横向溢出，打开记录不需要横向拖动。

## UX02：弹窗可见，但键盘仍在操作背景页面

**实测：** 点击主持稿“段落设置”后，焦点仍停留在背景的“段落设置”按钮；按 Tab 后，焦点进入背景第一句台词的“条目类型”选择框。按 Esc，弹窗仍然保持打开。

**影响：** 只用键盘的用户看着弹窗却在操作背后的表单，可能误改内容；读屏用户也缺少可靠的弹窗进入与退出流程。

**位置：** [Script.vue](../src/web/pages/Script.vue) 的段落设置弹窗只声明了 `role="dialog"` 和 `aria-modal`，没有实际焦点管理。[Characters.vue](../src/web/pages/Characters.vue) 的角色设置使用相似结构，本轮未单独操作复现。

**建议：** 统一弹窗组件。打开后进入合适的首个控件或标题；Tab 保持在弹窗内；Esc 取消；关闭后回到触发按钮；背景不可操作。已有 [ActionDialog.vue](../src/web/components/ActionDialog.vue) 已处理部分焦点与 Esc 行为，可以统一完善，而不是每页重复实现。

这是 W3C 模态弹窗模式所描述的关键行为。[参考：WAI-ARIA Modal Dialog Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)

**验收：** 不用鼠标完成打开、编辑、取消和保存；整个过程中焦点不进入背景。

## UX03：成员误删没有恢复机会

**实测：** 填写了姓名、UID 和制作职务后点击“移除”，成员卡片立即消失，没有确认框，也没有撤销按钮。表单随后按现有逻辑自动保存。

**影响：** 误点一次就需要重新填写。若被移除者是负责人或主投稿账号，相应身份也被清空，之后才在提交阶段发现。

**位置：** [PeopleEditor.vue](../src/web/components/PeopleEditor.vue) 的 `remove()` 直接删除整行；[Submit.vue](../src/web/pages/Submit.vue) 对表单变更自动保存。

**建议：** 优先提供“已移除某成员 · 撤销”，把已填数据暂时保存在本地撤销记录中；对负责人或主投稿账号额外说明影响。空白成员可以直接移除。无需对每一次低风险操作都弹确认框。

**验收：** 移除后可以恢复姓名、UID、职务和原身份；自动保存不能使撤销失效。

## UX04：错误提示没有形成修正路径

**实测：** 填写了基础资料和成员必填字段，但未选择负责人、主投稿账号时，点击提交，表单底部出现“请选择一位负责人；请选择一个主投稿账号”。焦点仍留在提交按钮，错误没有跳转链接，也没有字段级标记。

**影响：** 多成员长表单需要用户自己判断问题在哪里；通用错误被合并成一串文字，不能指向“第几位成员”。

**边界：** 普通 `required`、邮箱等原生 HTML 校验能提供浏览器提示。本项主要指自定义身份、UID 重复、职务匹配等跨字段校验，不是说所有字段都完全没有校验。

**建议：** 保留错误摘要，但每条可跳到相关成员或字段；字段旁显示具体原因，用 `aria-describedby` 关联。失败后移动焦点到摘要或第一处错误。成员区顶部常驻显示“负责人：未选 / 主投稿账号：未选”，减少提交时才发现遗漏。

**相关位置：** [Submit.vue 的 check()](../src/web/pages/Submit.vue)、[shared/models.ts](../src/shared/models.ts)。

**验收：** 用户从错误提示出发，一次点击或键盘操作能到达问题位置；提示包含必要的成员姓名或序号。

## UX05：主持稿更像逐句配置表，连续编辑成本偏高

**观察与测量：** 一句普通台词周围有约 **11 个控件**，包括类型、角色、文本、舞台提示、多人/分段及六个行操作按钮。在 1440 像素桌面下，单句区域高约 **250 像素**；390 像素手机下约 **459 像素**。即使每句只有十几个字，也要频繁滚动。

每句都显示“条目类型”“角色”“已保存 · v1”等重复标签，常用输入和低频管理操作具有相近的视觉存在感。手机样例中，第一句编辑区距离文档顶部约 1569 像素。

**影响：** 不利于通读前后文、核对节奏、连续分角色写作。功能越多，页面越长。

**建议：**

- 常态显示“角色 + 台词 + 保存状态”，未选中的台词紧凑呈现；编辑当前句时再展开必要控件。
- 类型切换、复制、拆分、合并、删除放入可用键盘访问的“更多”菜单；不要只在鼠标悬停时提供操作。
- 舞台提示为空时折叠，已有内容时显示摘要。
- 保留多人合说与分段，但用角色标签直接表达结果，避免每次都需要阅读表单结构。
- 保留现有 **Enter 新建台词，Ctrl / ⌘ + Enter 换行**；不增加新建段落快捷键。
- 手机提供随时可打开的目录入口，避免滚到底部后还要返回顶部找目录。

以上是效率改进建议，不是要求删减现有能力。建议用 30 句真实稿件做编辑、找章节和通读任务验收，记录滚动与操作次数，而不是只看空页面是否整齐。

## UX06：辅助文字偏小，部分文字对比度不足

**测量：** 多处说明和保存状态是 12 像素；浅棕文字 `#94807a` 在纸色 `#fffdf9` 上约 **3.67:1**，灰色 `#8b7c7c` 约 **3.92:1**。浅棕说明放在页面底色 `#f5f1eb` 上约 **3.32:1**。

这些组合用于实际说明、状态等信息，不只是装饰。小字加浅色会增加阅读负担，尤其在手机、低亮度和视觉能力较弱的情况下。常规小字号文字的 AA 对比度参考值为 **4.5:1**；本次不对整个网站作完整无障碍合规结论。[参考：WCAG 文字对比度](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)

**建议：** 保留现有暖色风格，调深信息性辅助文字；主要输入和长文本优先使用更易读的字号，次级说明通常保持 13–14 像素。不要把已保存、错误原因或上传限制做成难读的小字。

**位置：** [style.css](../src/web/style.css) 的 `.hint`、`small`，以及页面局部的同类浅色文本。

**验收：** 所有实际承载说明的常规文字达到适用对比度；200% 放大后仍能完成主要任务。

## UX07：手机按钮能点，但不够易点

**测量：** 主持稿的上移、下移、复制、拆分等行操作高约 **27.8 像素**，箭头按钮宽约 **34 像素**；相邻间距约 6 像素。它们是频繁使用的编辑操作。

**影响：** 触屏时容易误触，多个类似小按钮并排时更难精确选择。手机导航又将多个管理模块放进横向滚动栏，切换较远模块需要额外滑动。

**建议：** 高频触屏目标尽量达到约 **44 × 44 像素**，这是本项目建议的舒适目标，不是对所有控件的 WCAG AA 硬性下限。减少常驻行按钮后，用足够大的“更多”入口承接低频操作；移动导航显示当前模块和“切换模块”，或使用清楚的抽屉菜单。

WCAG 2.2 AA 的目标尺寸基准是 24 × 24 CSS 像素，并有间距等例外，因此这里不能仅凭“不到 44”就认定违规。[参考：Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)

**验收：** 真机单手完成角色选择、插入和移动台词，不依赖精细点击；主要导航有稳定的可发现入口。

## UX08：祝福语打包范围不够直观

**现状：** 未勾选时导出本活动全部内容，即使列表正在按关键词筛选；勾选后只导出选中项。翻页或重新加载会清空选择。页面已有小字明确说明，并非完全没有告知。

**问题：** “打包文本 ZIP / 打包音频 ZIP”本身不能表达当前到底下载哪些资料。用户需要记住“零选择代表全部”这一规则，搜索后很容易按当前屏幕内容理解范围。

**建议：** 把范围变成显式选择：“已选 N 份 / 当前筛选结果 / 本活动全部”，按钮显示“下载已选 N 份文本”。明确选择是仅当前页还是可跨页保持。提前显示数量和超出单次限制的原因。

**位置：** [WishReview.vue](../src/web/pages/WishReview.vue) 的 `exportHref()`、`load()` 及导出提示。

**验收：** 搜索、翻页、勾选后，按钮旁的范围与实际导出一致；用户不用阅读长说明来判断。

## UX09：上传缺少准备阶段与失败恢复的清晰反馈

**代码观察：** 选中视频后，先保存草稿、创建上传任务、读取视频时长，再开始传输分片。时长读取最多等待 12 秒，这期间界面主要显示“0% · 上传中”。分片还会自动重试，但没有单独说明当前是在准备、识别时长还是重试。

**影响：** 用户容易把正常准备误认为卡住。大文件失败后需要重新选择，当前没有界面级的断点继续入口。

**边界：** 本项依据 [WorkUpload.vue](../src/web/components/WorkUpload.vue) 的实际操作顺序。本轮没有重新进行慢网、1 GB 上传或断点恢复实测，不宣称所有上传都会卡 12 秒。

**建议：** 使用“准备投稿 → 读取时长 → 上传已完成 MB / 总 MB → 确认文件”分阶段状态。不能读出时长时直接说明可手动填写；重试时说明正在重试。更长远可提供可恢复上传，至少明确失败后需要重新选择文件。

**验收：** 上传前后等待均有准确状态；没有实际传输时不制造一个似乎停住的百分比。

## UX10：验证码重发、换邮箱和焦点衔接可以更清楚

**实测与代码：** 发送验证码后显示新输入框，但没有自动将焦点送入；“更换邮箱或重新发送”先返回邮箱阶段，重发还需要再点一次“发送验证码”。没有可见的重发冷却状态。

**影响：** 验证码步骤与下一步动作的衔接不够直接，用户不易区分是换地址还是给同一地址再发一次。

**建议：** 分成“重新发送”和“修改邮箱”；发送成功后聚焦验证码框，清楚显示发送目标。倒计时必须匹配服务端实际限流，不凭空设一个等待时间。已经实现的验证码自动填充属性应保留。

**位置：** [Login.vue](../src/web/pages/Login.vue)。

**验收：** 纯键盘可顺畅完成邮箱到验证码的切换；重发一次点击即可表达意图，发送中不能重复触发。

## UX11：审核工作适合单件操作，连续处理成本较高

**代码观察：** 审核详情没有“下一份待审核”；返回列表会重新建立搜索、状态和页码的本地状态。审核成功主要靠状态和内容变化体现，没有明确的结果条。通过操作直接提交；驳回有原因要求，但没有展示将发给投稿者的最终反馈摘要。

**影响：** 多份投稿连续处理时反复返回、重新筛选和找位置。通知与决定之间的关系也需要管理员自行从状态区域推断。

**建议：** 返回列表时保留筛选、分页和滚动位置；增加“下一份待审核”；成功后明确显示“已通过 / 已驳回，通知待发送”。对会触发投稿者通知的决定，提供简短的决定摘要或确认，避免无区别地给所有普通操作加弹窗。

若作品是上传视频，目前审核详情主要提供下载入口。站内播放可作为后续效率改进，但应先验证编码和权限支持，不把它描述为本次已验证的缺陷。

**位置：** [Review.vue](../src/web/pages/Review.vue)、[Submissions.vue](../src/web/pages/Submissions.vue)。本项是代码和任务路径分析，未进行真实审核人员的批量任务计时。

## 应保留的现有设计

- 页面标题已经直接表达功能；不恢复“把节目排成一场晚会”等宣传式标题。
- 投稿已按节目资料、作品交付、团队成员分组，可选说明折叠，方向是合理的。
- 成员只需填写一次，再标记负责人、主投稿账号和制作身份；不重新拆成多份重复表单。
- 主持稿已有目录、键盘新建台词、多人/分段发言和自动保存，应围绕连续编辑优化呈现。
- 有上传百分比、取消上传、保存状态、角色文字标签和可见焦点样式；不为简洁而去掉必要反馈。
- 管理员任免已有影响说明和确认；保持这种对重要动作解释清楚的方式。
- 日期时间使用原生选择控件；时长继续支持直接选择与键盘输入，不退回要求填写 ISO 字符串。

## 推荐改进顺序

1. **操作可靠性：** 先修上一份报告中 F01/F02 的保存与退出问题，同时补齐本报告 UX02/UX03 的弹窗焦点和撤销。
2. **任务能完成：** 修手机审核溢出、表单错误定位和文字可读性。
3. **常用任务效率：** 收紧主持稿每句占用的空间，整理手机触控与目录，明确祝福语下载范围。
4. **体验细节：** 优化上传阶段、验证码流程、审核连续处理。

建议保持现有品牌与暖色风格，统一优化页面结构、控件状态和恢复路径。第一轮无需整体重做视觉设计，也不建议给工作台添加装饰性动画或额外宣传文案。
